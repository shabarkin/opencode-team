This fork adds an experimental **Agent Teams** workflow on top of upstream OpenCode.
It lets one lead session coordinate multiple teammate sessions, each with its own context, tools, status, and optional isolated worktree.

:::note
This page documents the `feat/agent-teams` fork, not upstream `anomalyco/opencode`.
Enable the feature with `OPENCODE_EXPERIMENTAL_AGENT_TEAMS=1`.
:::

---

## Start here

```bash
OPENCODE_EXPERIMENTAL_AGENT_TEAMS=1 opencode
```

Optional isolated teammate worktrees:

```bash
OPENCODE_EXPERIMENTAL_AGENT_TEAMS=1 \
OPENCODE_EXPERIMENTAL_AGENT_TEAMS_WORKTREES=1 \
opencode
```

At a high level:

1. The lead creates a named team with `team_create`.
2. The lead spawns specialists with `team_spawn`.
3. Teammates coordinate through inbox-backed `team_*` tools.
4. The lead steers, reviews, and collects structured results.
5. The lead shuts the team down and, in worktree mode, merges each teammate branch before cleanup.

## Core concepts

### Lead session

The lead owns orchestration.
Once a team exists, the lead is expected to split work, steer teammates, monitor progress, and synthesize only after collecting results.

### Teammate sessions

Each teammate is a real child session with its own:

- agent
- model
- permission set
- prompt loop
- status and execution state
- optional worktree branch and directory

### Shared coordination state

Every team can use:

- a shared task board via `team_tasks` and `team_claim`
- a shared notepad via `team_notepad`
- durable inboxes for direct messages, broadcasts, plans, and results

### Review loops

This branch adds two built-in review patterns:

- **Plan approval**: spawn a teammate in read-only plan mode and unlock write tools later with `team_approve_plan`
- **Checkpoint review**: pause a teammate at configured boundaries, inspect progress, then resume or redirect them

### Steering

Steering is a non-destructive way to redirect work already in progress.
The lead can message, pause, resume, restart, or broadcast updated instructions without tearing the whole team down.

See [Steering](/docs/steering).

## Team lifecycle

### 1. Create the team

`team_create` establishes the team record and optional shared tasks.

Useful options include:

- `delegate`: keep the lead in coordination-only mode
- `collect_strict`: require fresh teammate results during collection
- `require_result_before_shutdown`: block shutdown until assigned work has a result
- `max_cost`: team-wide budget cap
- `output_format: single_synthesis`: force one consolidated final answer

### 2. Spawn teammates

`team_spawn` creates child sessions with a model, agent, prompt, and optional safety settings such as:

- `mode: research` for read-only investigation
- `require_plan_approval`
- `checkpoint`
- `timeout`
- `max_cost`
- `result_deadline`
- `claim_task`
- scoped file and bash access

### 3. Coordinate work

Teammates coordinate with:

- `team_message`, `team_reply`, `team_broadcast`
- `team_inbox`
- `team_tasks`, `team_claim`
- `team_notepad`
- `team_phase`
- `team_status`, `team_health`

Teammates can also request more help with `team_request_spawn` or run a lightweight private helper with `team_delegate`.

### 4. Review and collect

The lead can:

- approve or reject plans with `team_approve_plan`
- resume a checkpointed teammate with new instructions
- use `team_collect` to wait for structured results instead of redoing the work

### 5. Shut down the team

The lead uses `team_shutdown` or `team_shutdown_all`.
Shutdown can be deferred if teammates still have active assigned work and fresh results are required.

### 6. Merge and clean up

In shared-directory mode, cleanup can happen after shutdown.
In worktree mode, the lead must run `team_merge` before `team_cleanup`.

See [Worktrees](/docs/worktrees).

### Component diagram

```text
Lead session
  │
  ├─ team_create / team_spawn / team_collect / team_shutdown*
  │
  ▼
Team state (Storage-backed)
  ├─ members + lifecycle
  ├─ TeamTasks shared board
  ├─ TeamNotepad shared context
  ├─ Inbox JSONL per recipient
  ├─ TeamMessaging delivery + recovery
  ├─ TeamScope permission shaping
  ├─ TeamFiles conflict detection
  └─ TeamWorktree / TeamMerge
        │
        ├─ /team HTTP routes
        ├─ /event stream → TUI sync refresh
        ├─ session steering/message routes
        └─ UI cards for team tool results
```

### Spawn flow

```text
lead calls team_spawn
  → team policy checks
  → effective scope is computed
  → optional worktree is created
  → child session is created with team-aware permissions
  → teammate record is stored
  → notepad/tasks/peer context is injected as a user message
  → teammate prompt loop starts in the background
```

### Delivery flow

```text
teammate claims or receives work
  → teammate reports progress with team_message / team_phase / team_tasks
  → teammate sends final structured result with team_submit_result
  → lead waits with team_collect
  → lead produces one final synthesis
  → lead shuts team down
  → worktree teams merge branches, then cleanup
```

## Safety, isolation, and recovery

### Tool and permission isolation

- Teammates cannot create nested teams.
- Lead-only tools are explicitly denied for members.
- Restrictive teammate agents still receive explicit allow rules for member-safe `team_*` tools.
- Research mode and plan mode lock write surfaces.
- Team-linked child tasks do not get team messaging rights; at most they receive read/list access to `team_notepad`.

### Freshness checks

This branch tracks when a teammate was last assigned work and when they last submitted a result.
`team_collect` and shutdown guards can require a result newer than the latest assignment.

### Durable delivery

Team messages are first written to inbox storage, then injected into the recipient session.
That keeps coordination resilient across restarts and delayed delivery.

### Restart recovery

Bootstrap recovery restores team state after server restarts, replays unread messages, and warns the lead when teammates need to be resumed.

### Conflict detection

Recent file edits are tracked per teammate.
In shared-directory teams, overlapping edits can raise warnings or trigger policy action.
In worktree teams, the same relative path can still collide later during merge.

## Operational notes

- The feature is fully gated behind `OPENCODE_EXPERIMENTAL_AGENT_TEAMS=1`.
- Worktree mode is separately gated by `OPENCODE_EXPERIMENTAL_AGENT_TEAMS_WORKTREES=1`.
- `/team` routes require the caller session in `x-opencode-session`.
- Teammates should communicate through `team_*` tools; plain text replies are not enough for the lead to consume.
- This fork keeps the feature experimental, so tool names and route details can still change.
